案例一：富文本编辑器功能增强

需求描述

  • 支持单元格设置背景色
  • 支持分页功能

核心问题：不想改动源码，该功能已上线且写在公共组件里，不宜改动底层

探索目标

在不改动源码的前提下进行功能增强

原富文本编辑器界面

召唤"专家"

使用Workbuddy的专家模式，召唤一个"前端专家"

提示词中包含想实现的功能的截图和自己的需求描述

Review方案

人工预览方案，看是否合适或者需要调整

方案确定后，让Wordbuddy生成Markdown文档保存到本地

交付Claude Code

将方案文档交付给Claude Code，写好需求背景、Markdown文档地址

经过多轮对话，成功实现了富文本编辑器的功能增强

完成功能

多轮对话中的问题

幻觉问题：AI多次表示"找到问题了"，但实际并没有解决问题

失忆问题：上下文过长导致AI遗忘之前的信息

时间消耗：实现这个功能基本上消耗了两个下午的时间，总计大概一天时间

案例一经验总结

核心经验：要及时清理上下文，因为在处理一个复杂的任务时，可能在对话的过程中产生一些错误的方案，一旦上下文过长，除了本身会产生幻觉，这些错误的方案也会污染上下文。

案例二：UniApp组件自研

需求描述

自研拍照组件，省去选中图片的步骤

原：拍照 → 选中图片 → 上传 → 改1：拍照 → 选中图片 → 调起编辑器 → 涂鸦 → 上传
改2：拍照 → 调起编辑器 → 涂鸦 → 上传

问题：uniapp上传组件不支持自动"选中图片"，即使用底层方案也无法解决

自研组件的挑战

需要推翻原来的上传组件，基于原生App自研一套拍照组件（参考微信、小红书的拍照组件）

工期不允许立刻自研的原因：

  • 不具备成熟的原生App开发能力
  • 兼容性问题无法评估
  • 不了解uniapp对原生组件、原生API的支持程度
  • 不确定前端技术栈能否解决此问题

尝试过程

使用Minimax-2.7、Hy3-preview都没有解决

最后尝试GLM-5V-Turbo模型

实现过程

查看官方文档，可以使用live-pusher组件进行实时音视频录制

遇到的问题

调用摄像头时控制台一直报错，有兼容性问题

最终解决方案

通过与AI多轮对话发现：
live-pusher组件 + nvue
既能解决兼容性问题，也能解决原生组件的开发问题

案例二经验总结

核心经验：AI Coding一定要结合自身工作经验，要善于引导AI做正确的事情，不能完全依赖AI，也不能完全依赖同一个模型。

自研通用的MCP Server

从0到1设计并落地一个通用的MCP Server：fetch-article

背景

  • 公司内部的MCP管理平台无法满足前端需求
  • 平台只支持Python
  • 不支持更深层的文件资源的嵌套

前端需求

  • 希望使用JavaScript来开发MCP Server
  • MCP Server可能包含更多的层级目录和文件

MCP管理平台（代码块形式）

前端MCP Server（项目形式）

fetch-article MCP Server

功能描述：在智能体应用中只需输入url，即可解析url中所有内容，并按照skill中设定的规格进行内容的格式化输出，方便快速学习各个技术平台的博客内容。

实现架构

集成到智能体应用

因为fetch-article是一个通用的MCP Server，所以可以集成到任何智能体应用中

集成到Claude Code

{
  "allowedMcpServers": [{
    "serverName": "fetch-article"
  }]
}
{
  "mcpServers": {
    "fetch-article": {
      "args": ["/c", "node", "D:/workspaceAI/fetch-article/server.mjs"],
      "command": "cmd",
      "type": "stdio"
    }
  }
}
